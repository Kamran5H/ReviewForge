# ReviewForge

A framework for building **critical, reproducible review articles on any topic** — the
generalised, config-driven engine distilled from the zinc–air review project.

## Read this first: what this code is, and what it is not

The zinc–air review was not produced by a script. It was produced by a *loop*: deterministic
tools did the mechanical work (harvesting, screening, citation resolution, compilation,
verification), and at every point that required **judgement** — is this coupling real? is
this citation right? is this claim over-stated? does "in air" mean the cell's atmosphere or
a furnace step? — a reasoning step (a human, or a language model reading with comprehension)
made the call.

**ReviewForge encodes the mechanical loop and marks every judgement point.** It does not
replace the judgement. Run it on a new topic and it will give you a fast, structured,
reproducible *draft with a full audit trail* — the same starting point the first
`review_builder.py` gave, but organised so the judgement steps are explicit and cheap to do
well. The quality still comes from doing those steps carefully, not from the code.

If you take one idea from this framework, take this: **every number a review reports should
be regenerated by a script, and every claim it makes should name the evidence.** The tooling
here exists to make that the path of least resistance.

## What it generalises from the zinc–air build

| Zinc–air artefact | Generalised module | What it does for any topic |
|---|---|---|
| `Articles_v2.py` | `harvest.py` | Multi-API open-access literature retrieval, relevance-gated |
| `_cache_text.py` | `textcache.py` | PDF → text cache; every screen reads from here |
| `_screen.py`, `_reporting_screen.py` | `screen.py` | **Reproducible lexical screen** — config-defined items, per-paper output, subset denominators. The signature methodology. |
| `_resolve.py` | `resolve.py` | **Length-aware citation resolver** — the fix that stopped miscitations |
| `_crossref.py` | `crossref.py` | Bibliographic enrichment (volume/pages/year) with a polite pool |
| `_validate_dump.py`, `_validate_result.py` | `validate.py` | **Read-by-hand validation harness** — draws a seeded random sample, dumps evidence for a human/LLM to classify, scores agreement (Cohen's κ) and a confusion matrix |
| `_figs_own.py` | `figures.py` | Original data figures from the corpus, not reproduced panels |
| `_compile.py`, `_topdf.py` | `compile.py` | Sections + tables + figures → Word → PDF |
| `_verify_refs.py`, humanization scans | `verify.py` | Integrity suite: reference audit, number-vs-script consistency, machine-writing tells, unresolved markers |
| the LLM drafting (`review_builder.py`) | `llm.py` + `stages.py` | LLM-backed judgement stages behind one interface (Ollama / OpenAI-compatible / Anthropic) |
| hundreds of instructions | `pipeline.py`, `config.py` | The orchestration and the per-project config that makes it topic-agnostic |

## The eleven principles the zinc–air project taught, encoded as checks

1. **Every quoted number regenerates from a script.** `verify.py` fails the build if a
   reported figure has no backing script output.
2. **Screens are lower bounds, and say so.** `screen.py` labels every percentage.
3. **Validate the machine against reading.** `validate.py` is mandatory before any screen
   percentage is promoted from "the screen finds" to "we find".
4. **Resolve citations length-aware, keyed on the resolved paper.** `resolve.py`.
5. **Own figures, not borrowed panels, carry the argument.** `figures.py`.
6. **Attack your own thesis.** `stages.py::adversarial_review` prompts the LLM to refute the
   paper's central claim and quantify it against the corpus.
7. **State confidence intervals on small samples.** `verify.py` flags bare correlations.
8. **Disclose AI use; never conceal it.** `compile.py` writes the declaration; `verify.py`
   refuses to remove it.
9. **Never distribute copyrighted full text.** `deposit.py` excludes the text cache.
10. **No stale numbers.** `verify.py` cross-checks every denominator across sections.
11. **Humanise the prose; keep the method.** `verify.py` scans for machine tells but never
    touches the Methods.

## Quick start

```bash
pip install -r requirements.txt
python -m reviewforge init my_review              # scaffolds a project + config.yaml
#   edit my_review/config.yaml : topic, keywords, section plan, screen items, LLM backend
python -m reviewforge run my_review --stage harvest
python -m reviewforge run my_review --stage screen
python -m reviewforge run my_review --stage validate     # human/LLM reads the sample here
python -m reviewforge run my_review --stage draft        # LLM drafts sections from evidence
python -m reviewforge run my_review --stage compile
python -m reviewforge run my_review --stage verify       # gate before you trust anything
```

Each stage writes an audit file. Nothing downstream trusts an unverified upstream number.

## Honest limitations

- The **thesis** is the paper. ReviewForge can *prompt* an LLM to propose and attack one
  (`stages.py`), but a novel, correct thesis is not guaranteed by any pipeline. It is the
  one thing you must own.
- **Reading 30–60 papers by hand** (`validate.py`) is not optional and not automatable-away.
  It is the step that separates a real review from a plausible one.
- The LLM stages need a backend and will cost tokens or local compute. Configure in
  `config.yaml`.
